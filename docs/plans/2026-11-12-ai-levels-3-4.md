# AI levels 3 and 4: Act and Watch, within gates (Implementation Plan)

> **For agentic workers:** use superpowers:subagent-driven-development. One implementer per task, a review per task, a whole-branch
> review at the end of each release. Steps are test-first: write the failing tests, see them red, then make them green. Run targeted tests
> only; never a full suite.

**Goal:** the AI acts on its own only where it has earned it, only with the mildest steps, with a person able to confirm or undo each
action, and with the lint ban on the AI module intact. Delivered in four releases, in this order, each safe to ship alone:
**R1** the seams and a read-only gate dashboard (nothing acts); **R2** shadow mode (everything runs, nothing is written to a player);
**R3** acting; **R4** Watch (level 4, files reports only; separate go-ahead). The site wording and the "Using the AI responsibly" page follow R3.

**Architecture:**
- `packages/core/src/ai/` (the model and the proposals; lint-banned from the writers) gains `gates.ts` (pure), `reach.ts` (pure), `actPlan.ts` (pure preconditions, holdback, caps),
  the `ActionProposer` type, and a confirming-read purpose. It never imports a writer and never calls one.
- `packages/core/src/aiActor/` (new; the ONLY place a sanction with `source: 'ai'` is written) gets `service.ts` (`AiActionService`), `recheck.ts` (recomputes everything from the store),
  `write.ts` (one transaction: action row, sanction group, notice) and `review.ts` (confirm, undo, undo-all). It imports the sanction code and the AI module's types and pure functions;
  it never calls an adapter.
- `chatwarden.ts` wires them and exposes `cw.ai.gates()`, `cw.ai.acting`, `cw.ai.actions`, `cw.people.automation`.
- Store: new optional methods, memory and SQLite, one shared contract suite `test/contract/ai-act.contract.ts`; three migrations (one per release; numbers assigned at merge).
- `@chatwarden/http` gains the routes of design 6.6 and three lowerable permissions (`ai.review`, `ai.pause`, `automation.write`).
- `@chatwarden/hub-react` gains the gate table, the shadow status, the "Acted by AI" view, the owner dialog and the Person page mark. `@chatwarden/player-react` gains two notice fields and five words.

**Spec:** `docs/design/2026-11-12-ai-levels-3-4.md` (section numbers below refer to it), including its closing Rulings section. Also binding:
`docs/design/2026-11-11-ai-levels-1-2.md` (sections 8 and 12, addenda A1 to A18), `docs/design/2026-11-12-appeals-and-names.md` (4.3 to 4.5 and the revoke-only ruling),
`docs/design/2026-11-12-flood-control-and-signals.md` (5.7), `docs/design/2026-11-10-hub-workbench-and-teams.md`.

## Global Constraints
- Rules from `AGENTS.md` and `CLAUDE.md`: Apache-2.0 and DCO (`git commit -s`), ESM, `erasableSyntaxOnly` (no parameter properties, no enums), every time from the injected `Clock` (no
  `Date.now()` in package code), core imports nothing from `node:` but `node:crypto` and has no runtime dependency, synthetic terms only (zorbak, vlemmo, quissel, drakkuun, fenrisk, tarvo,
  snerp, glarn), test-first, **targeted test runs only** (never an unfiltered `vitest run`; the package gate `npx vitest run packages/<pkg>` once at the end of a task), `npm run lint` and
  `npm run typecheck` before every push. With more than one agent in the worktree: commit by pathspec, `git add` new files first. Branch `ai-act`, worktree `C:\dev\chatwarden-wt\ai-act`.
  One branch per release (`ai-act-r1`, `ai-act-r2`, ...) so each merges and ships on its own.
- **Sequencing and Step 0 (before Task 1 of each release).** Rebase on `main`. Check that appeals and names (0.1.9) are on `main` (`cw.appeals`, `markReversed(reportId, { corrective })`,
  `appeals.stats()`, `AppealRow.group_id`, migration 22). **R1 may be built before appeals merges** (every appeals-derived number reads "not available" and no cell can open), but R2 and R3 must not
  merge before it. If a name used below is missing on `main`, stop and report; do not recreate it. Migration numbers: use the next free number after the highest on `main` (23 if appeals' 22 is
  the last); version labels are assigned in merge order and the numbers below are expectations.
- **The ban and the seam are the point.** Nothing under `packages/core/src/ai/` imports `decide`, `sanctions`, `strikes`, `mutes` or `notices`, or calls a store writer (Task 1 adds the second lint rule).
  Only `packages/core/src/aiActor/` writes `source: 'ai'`. A task that needs to cross the line stops and says so.
- **The ceilings are constants, not options.** 24 hours, the kinds (warning, chat), no ban, the own-line rule, "do not automate", "only people review" have no band and no config. Tests pin each.
- **No gate number comes from a client.** The hub, an adapter and a request body never supply a count, a rate or a state; the server computes them from the store at the moment of use.
- **No identifier in a player response.** Seed distinctive client keys, subject ids, action ids, read ids and moderator refs; none may appear in any player route's body or headers (Task 16).
- **Fail soft toward the human.** Any error in the act path means no action and a logged class; the report stays in the human queue exactly as at level 2. An AI-side failure never fails a report, a
  decision or a player's ack.
- **UI rule (clean core, power behind one door).** The only always-visible addition is one neutral chip in the Cases header (shown only when something awaits review). Everything else is behind the Filters
  drawer, Settings > AI > Advanced, the case's `...` menu or the Person page `...` menu. Every string through `t()`. Colour only where it means something (blue = your next action, red = overdue).
  Check in a real browser at desktop and 360 px, light and dark, for Tasks 7, 12 and 17.
- All new public names are `@experimental` in TSDoc and listed so in the READMEs until 0.2.
- Privacy of the plan itself: nothing outward. No push, no publish, no tag, no site deploy without the maintainer's go-ahead.

## Review Focus
Six failure modes the happy-path tests would not exercise; each has its test in the owning task.
1. **The seam leaking.** Any way the AI module (or a caller) can write a sanction, a notice or a decision without the actor: a store method reachable from `ai/`, a public entry that accepts `source: 'ai'`,
   a second call site of `automated: true`. Tasks 1, 14.
2. **The ceilings enforced once, not twice.** The actor must recompute the step and call `assertWithinCeilings` itself, and refuse (not correct) a proposal that disagrees. Tasks 11, 14.
3. **A gate trusting its inputs.** Any number read from a request, a cached flag, or a count that includes the AI's own confirmed actions in the earn population. Tasks 2, 3, 4, 15.
4. **Double action and half action.** Two processes, a retry after a crash, a confirm racing an undo, an undo after expiry: exactly one sanction, one notice, one action row, and no state where the row
   and the sanction disagree. Tasks 14, 15, 18.
5. **Wording that implies a person looked.** Every notice and restricted-line state, every locale key. Task 16.
6. **Pausing that does not pause.** The kill switch must act before the very next act, across processes, even with a fresh policy cache and a queued action. Task 18.

## Order and parallelism
**R1:** Task 1 first. Tasks 2, 3 and 5 are independent after it and can run at once. Task 4 follows 2 and 3. Task 6 follows 4 and 5. Task 7 follows 6. Task 8 last.
**R2:** Task 9 first. Tasks 10 and 11 follow 9 and can run at once. Task 12 follows 11. Task 13 last.
**R3:** Task 14 first. Tasks 15 and 16 follow 14 and can run at once. Task 17 follows 15 and 16. Task 18 follows 15. Task 19 follows 17 and 18. Task 20 last.
