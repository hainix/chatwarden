# The chat box and the room broadcaster

Today Chatwarden moderates the chat a game already has. A game with no chat at all has nothing to adopt. This note adds the missing half:
a drop-in `<ChatBox>` for players (in `@chatwarden/player-react`) and a small room broadcaster (in `@chatwarden/http`), so a game can add
chat that is moderated from its first line and reach the moderator hub with no further work. Both ship inside the packages that exist
today. The core engine is not touched.

It answers the follow-up "Chat box" in `docs/plans/follow-ups.md` and ruling 1 of `docs/design/2026-11-11-site-copy-rewrite.md`: the
site headline changes to promise chat only after this ships. It builds on `docs/design/2026-11-09-product-scope.md` section 10 (the
optional chat layers), and deliberately takes only the smallest slice of it (section 2).

## 1. Why

**The promise.** The owner (2026-11-09, product scope section 10): "someone just wants to throw in chat and hook up their buttons or
just take our default buttons. Nice to give as much out of the box that works as possible." And for the site (2026-11-11): "quickly
adding chat along with moderation into your game, then a hub to moderate." The kit has the second half (the hub) and the middle (the
check, notices, reports). It has no first half. The headline cannot say "add chat" while an adopter must build a transport, a list, an
input, a refusal display and a report entry point before the kit does anything.

**What an adopter writes today.** `examples/tiny-chat/server.ts` is the honest measure: a WebSocket server, a seat table, a fan-out loop
that calls `cw.chat.visibleTo` per viewer, a frame protocol, `refused` frames that must carry the right fields and none of the wrong
ones, a `/report` route, a notice push. About 300 lines, all of them easy to get subtly wrong (an id leaked in a frame, a refused line
echoed to the room). tiny-chat has no browser client at all. The kit's rules about what may reach a player are enforced by the adopter's
discipline. This note moves that discipline into the kit.

**Why not a bigger chat product.** Product scope section 10 sketches `chat-server`, `client`, `chat-react` and `translate` packages with
channels, whispers, typing, presence, reactions, pins and translation. That is a product, and it needs four new npm packages, each of
which the release workflow's OIDC trusted publishing cannot publish until the owner publishes it once by hand. This note ships the part
that makes the headline true (one room, lines in and out, history for late joiners, refusals shown to their author, report and mute on a
line) and stops there.

## 2. Goals and non-goals

### Goals
- A game with no chat adds moderated chat with about a dozen lines on the server and about eight in the client.
- Every line goes through `cw.chat.accept` before anyone but its author can know it exists. A refused line is shown only to its author,
  as a reason, never as text, never to anyone else.
- A late joiner (or a reconnecting player) sees recent lines, bounded in count and age, with their own mutes applied.
- Report and mute on any other player's line, using the existing `ReportDialog` and the kit's existing mutes.
- A player who cannot chat (restricted) sees the existing `RestrictedChatLine`; a player with notices gets the existing `NoticeQueue`
  nudged to refresh. No second implementation of either.
- Accessible, themeable like the other player components, English words first through the existing flat catalog, clean at 360 px.
- A game with its own socket (Socket.IO, Colyseus, a plain `ws`) can plug in by implementing two small interfaces.
- No new npm package, no migration, no change to `@chatwarden/core`, no peer-floor rise.

### Non-goals
- No channels, whispers, DMs, team chat, spectators, typing indicators, presence, read markers, reactions, pins, edit or delete,
  translation, quick chat, emoji picker, markdown or links. One room is one list of lines (section 16).
- No moderator removal of a line from the room (the hub acts on reports, as today). No shadow banning (a product non-goal).
- No shared state across processes (section 10).
- No persistence of chat text. The kit's own evidence buffer and report excerpts are unchanged.
- No change to how the hub or the staff routes work.

## 3. Rulings (decided; the details below follow from them)

1. **Ruling: it ships inside existing packages only.** `<ChatBox>` and its client transport live in `@chatwarden/player-react`, reached by a
   new subpath `@chatwarden/player-react/chat` (and `/chat.css`). The broadcaster and its routes live in `@chatwarden/http`, reached by
   a new subpath `@chatwarden/http/chat` and also exported from the root. There is no new package, no store change (so no migration),
   no change to `@chatwarden/core`, and no peer floor rises: both packages use only names core already exports.
2. **Ruling: the default transport is Server-Sent Events down and `POST` up.** The client reads the stream with `fetch`, not
   `EventSource`, so the adopter's header-based auth works. A game with its own socket implements `ChatTransport` (client) and writes
   to a `ChatSink` (server); both are small and public (section 5.3).
3. **Ruling: identity is the adopter's, through the hook the player routes already use.** `chatRoutes` takes the same
   `identify(req) => RawWho` as `playerRoutes`, plus one required `join(req, roomId, who)` hook that says whether this player may enter
   this room and under what display name. Nobody is identified by the kit and no credential is kept (section 11).
4. **Ruling: one check for every line, and only the author hears a refusal.** A line is checked by `cw.chat.accept(roomId, seat, text)`
   and nothing else decides delivery. A refusal answers the author's request with the reason, and where the check gave them
   `until`, `byModerator`, `rule`, `noticeId` and `retryAfterMs`. It never carries the text, and nobody else's stream hears of it.
5. **Ruling: a mute is silent.** `muted` is not a refusal. A mute hides the muted player's lines from the muter; the muted player is
   never told and sees no change. A player a moderator has silenced is `restricted` (a sanction), and gets the existing line for it.
6. **Ruling: history is a bounded in-memory ring per room, per process.** At most 50 lines and never older than the kit's evidence
   window (`EVIDENCE_MAX_AGE_MS`, 15 minutes), so history never shows a line the kit can no longer evidence for a report. It is filtered
   per viewer when it is sent. No store table, no persistence (section 9).
7. **Ruling: the wire carries no identifier.** A line on the wire is `{ id, at, name, text, mine? }`. There is no seat id, subject id,
   client key, hash, IP or account id in any frame, response, header or log. `id` is the room's line counter, as in the kit's evidence.
   `name` is the display name the game's `join` hook chose to show other players (section 11).
8. **Ruling: the report and mute actions name a line, never a person.** The server resolves a line id to its author from its own ring (the one exception is undoing a mute, which names the opaque token the server gave the muter).
   The reporter's seat comes from the request's identity and never from the body.
9. **Ruling: the box is clean; power is behind one door.** The always-visible UI is a list, one input and one Send button. Per line there
   is one small options control (Report, Mute). Everything else (muted players, the chat standard, rules link) is behind one
   "Chat options" control. No new always-visible badge, toggle or counter (the owner's rule, 2026-11-11).
10. **Ruling: the ChatBox is a lazy subpath, not part of the main entry.** `@chatwarden/player-react` (the main entry) is unchanged and
    stays under its 10 KB budget. The chat entry has its own measured budget (section 13.5). Its code is reachable with one dynamic
    `import()`.
11. **Ruling: refusal reasons on the wire are an open string.** The client has words for every reason the kit has today and for the
    three coming with slow mode (`slow_mode`, `flood`, `duplicate`), and a generic sentence for any reason it does not know. The chat
    box works the same whether flood control has shipped or not (section 8.3).
12. **Ruling: multi-process is sticky rooms in this release.** Route a room's connections to one process, as pacing already advises.
    A pub/sub hook is described (section 10), not shipped.
13. **Ruling: the broadcaster imports nothing from `node:`.** `@chatwarden/http/chat` can run in a browser tab (the site demo runs the
    real kit in the page), like `@chatwarden/http/admin`. Only the Express adapter, which already exists, is Node.
14. **Ruling: tiny-chat gets the HTTP chat beside its WebSocket protocol, and a browser page that uses the ChatBox.** The WebSocket
    protocol and its tests are untouched. The site demo adopts the ChatBox in its own later PR (section 18, question 7).
15. **Ruling: the owner's UI rules apply.** Colour only where it means something (blue for "you" and the next action; red for a failure),
    every string through `t()`, checked at desktop and 360 px, light and dark.

## 4. Five minutes: what an adopter writes

**Server** (Express; the kit's other routes are mounted as today):

```ts
import { chatRoutes, createRoomBroadcaster } from '@chatwarden/http';
import { toExpress } from '@chatwarden/http/express';

const chat = createRoomBroadcaster(cw); // in-memory history; one process
app.use(
  '/chat',
  toExpress(
    chatRoutes(cw, chat, {
      identify: (req) => ({ accountId: yourSession(req)?.userId, ip: req.remoteAddress }), // the same hook as playerRoutes
      join: (req, roomId) => {
        const s = yourSession(req);
        return s ? { name: s.displayName } : null; // null: not allowed in
      },
    }),
    { fallthrough: false },
  ),
);
// Optional, one line: the game's platform.notify also nudges the open chat boxes to refresh notices.
// platform: { identify, notify: (subject) => chat.noticePending(subject) }
```

**Client** (React):

```tsx
import '@chatwarden/player-react/styles.css';
import '@chatwarden/player-react/chat.css';
import { lazy, Suspense } from 'react';
import { sseTransport } from '@chatwarden/player-react/chat';

const ChatBox = lazy(() => import('@chatwarden/player-react/chat').then((m) => ({ default: m.ChatBox })));
const transport = sseTransport({ baseUrl: '/chat', credentials: 'same-origin' });

<Suspense fallback={null}>
  <ChatBox room="lobby" transport={transport} reporting={rules.reporting} onNoticePending={() => setNoticeKey((k) => k + 1)} />
</Suspense>;
```

The moderator hub, the notices, "My record" and the rules page are the existing pieces. `cw.chat.accept`, the matcher, the profile, strikes,
automatic timeouts, mutes and reports all run, because the broadcaster calls the same facade the adopter's hand-written chat would.

## 5. Transport

### 5.1 What was weighed

| | Server-Sent Events down + POST up | WebSocket via an adopter-provided socket |
| --- | --- | --- |
| New dependency in `@chatwarden/http` | none | `ws` is not a peer of http today; the adopter's own socket would have to be wired by hand |
| Through proxies, CDNs, corporate firewalls | plain HTTP; works wherever a long response is not buffered; one `x-accel-buffering: no` header covers nginx | needs an `Upgrade`; some proxies and platforms (many serverless hosts) refuse or time it out |
| Express and plain `node:http` | yes: a response that stays open | needs a separate upgrade handler on the `http.Server`, outside `app.use` |
| Auth | the same `identify(req)` as every other kit route, on every request (cookie or header) | one check at upgrade; later frames are trusted, so each needs a seat lookup; `identify` runs against an upgrade request, which has no body and different timing |
| Browser support | `fetch` streaming; no `EventSource` needed | native |
| Direction | one way down; up is a normal request, which is easy to rate limit, log by status and replay-protect | two-way |
| Reconnect | the client re-requests; the server sends a fresh snapshot | same |
| Cost per line (up) | one small HTTP request (headers, about 300 bytes) | a frame |
| Fits "a game with no chat" | yes | yes, but the adopter writes the server |

Chat is low volume (3 lines per 5 seconds per player is the hard rate limit). The extra cost of an HTTP request per line is invisible at
that rate, and every one of those requests passes through the same rate limit, body limit and `identify` hook the other kit routes
use. A WebSocket gives nothing chat needs, and costs a dependency, an upgrade path and a second auth story.

### 5.2 Recommendation

**Server-Sent Events down, `POST` up, read with `fetch`.** Not `EventSource`: `EventSource` cannot send headers, and `identify` in this
kit reads headers (tiny-chat's `x-chatwarden-key`, a bearer token) as often as cookies. The client parses the stream itself (a 40-line
parser); that also gives abort, back-off with jitter and one place to read `retry-after`.

The stream sends a full snapshot on every connect, so a reconnect needs no `Last-Event-ID` machinery: the client merges the snapshot
by line id. One epoch string in the first frame tells the client when the server restarted (ids begin again at 1), so it can discard
what it holds.

### 5.3 The seam for a game's own socket

Both ends are interfaces. The default SSE implementation is one implementation of each.

Server: the broadcaster does not know about HTTP. It writes frames (plain objects) to a `ChatSink`. `chatRoutes` is one adapter that
turns frames into SSE text. A game with Socket.IO or Colyseus does not use `chatRoutes`; it calls the broadcaster from its own handlers:

```ts
// Socket.IO, sketch: everything between the socket and the kit is the broadcaster's job.
io.on('connection', (socket) => {
  const who = yourWho(socket);
  const session = chat.session('lobby', who, { name: yourName(socket) });
  if ('refused' in session) return socket.emit('chat:refused', session.refused);
  const stream = session.open({ write: (frame) => socket.emit('chat:frame', frame) });
  socket.on('chat:send', async (text, ack) => ack(session.send({ text })));
  socket.on('chat:report', async (input, ack) => ack(await session.report(input)));
  socket.on('chat:mute', (input, ack) => ack(session.mute(input)));
  socket.on('disconnect', () => stream.close());
});
```

Client: `ChatBox` takes a `ChatTransport` (section 6.4). A game with its own socket wraps it (open a connection, forward the frames,
implement `send`, `mute`, `report`). The frames are the same JSON objects either way.

## 6. API

### 6.1 The wire types (`@chatwarden/http/chat`, copied in player-react)

```ts
// packages/http/src/chat/wire.ts. The client has a copy (packages/player-react/src/chat/wire.ts); a test keeps the two assignable.

/** The version of the frames below. A change that breaks a reader raises it. */
export const CHAT_WIRE_VERSION = 1;

/** One delivered line, as a viewer sees it. No seat, no person, no hash. */
export interface WireLine {
  /** The room's line number (the kit's evidence line id). Unique within one `epoch`. */
  id: string;
  /** When the server accepted it, epoch ms. */
  at: number;
  /** The display name the game's `join` hook gave this player. */
  name: string;
  /** The text as delivered (after the profile's profanity mode: starred text is starred here). */
  text: string;
  /** Present and true on the viewer's own lines. */
  mine?: true;
}

/** The restriction on the viewer's own chat, or null. Same meaning as `RestrictedChatLineProps`. */
export interface WireRestriction {
  /** Epoch ms it ends, or null when it does not end on its own. */
  until: number | null;
  /** True when a moderator set it; false for the automatic filter. */
  byModerator: boolean;
}

/** A player the viewer muted, by an opaque token only the viewer can use to undo it. */
export interface WireMuted {
  ref: string;
  name: string;
}

/**
 * Why a line was not sent, for its author. `reason` is one of: `length`, `rate`, `gate`, `restricted`, `blocked`, `profanity`, `banned`,
 * `empty`, and, once pacing ships, `slow_mode`, `flood`, `duplicate`. A reader treats any other string as unknown.
 * Never carries text, a handle, an id or a moderator's note.
 */
export interface WireRefusal {
  reason: string;
  /** `restricted` and `banned`: epoch ms it ends, or null. */
  until?: number | null;
  byModerator?: boolean;
  /** The Community Rule number to show as "Community Rule N". */
  rule?: number;
  /** The player's own notice that explains it (look it up with the player routes). */
  noticeId?: string;
  /** `slow_mode`, `flood`, `duplicate`: when to try again, ms from the answer (a whole number, 1 or more). */
  retryAfterMs?: number;
}

export type ChatFrame =
  | {
      type: 'hello';
      v: typeof CHAT_WIRE_VERSION;
      /** Changes when the server restarts or the room is closed and reopened. */
      epoch: string;
      room: string;
      you: { name: string };
      /** The line length limit (`cw.limits.chatMaxLength`), for the input. */
      maxLength: number;
      /** `cw.summary`: the profile's one-line standard. */
      summary: string;
      restriction: WireRestriction | null;
      /** Recent lines the viewer may see, oldest first. */
      lines: WireLine[];
      muted: WireMuted[];
    }
  | { type: 'line'; line: WireLine }
  /** Lines to remove from view (the viewer muted their author). */
  | { type: 'hide'; ids: string[] }
  /** The viewer's own state changed (a sanction landed, a mute was made from another tab). */
  | { type: 'state'; restriction: WireRestriction | null; muted: WireMuted[] }
  /** A notice is waiting for this player: ask the player routes for it. Carries nothing else. */
  | { type: 'notices' }
  /** The server is ending this stream. `banned` carries when the ban ends. */
  | { type: 'bye'; reason: 'banned' | 'room_closed' | 'shutdown'; until?: number | null };

export type SendResult = { ok: true; line: WireLine } | { ok: false; refused: WireRefusal };
export type MuteTarget = { lineId: string } | { ref: string };
export type ReportOutcome =
  | { ok: true; remaining: number }
  | { ok: false; refused: ReportRefusal | 'not_found'; remaining?: number }; // ReportRefusal is core's
```

### 6.2 The broadcaster (`@chatwarden/http/chat`, browser-safe)

```ts
import type { Chatwarden, Logger, RawWho, SubjectId } from '@chatwarden/core';

/** The game's description of a player in a room. */
export interface ChatMember {
  /** The display name other players see. 1 to 32 characters; control characters are removed. Checked with `cw.names.check` (see `nameCheck`). */
  name: string;
  /** Room tags passed to `cw.rooms.seat` (for example `{ mode: 'ranked' }`). */
  tags?: Record<string, string>;
}

/** Where frames go: an SSE response, a socket, a test. */
export interface ChatSink {
  /** Deliver one frame. Return `false` when the receiver is backed up; the broadcaster drops a stream that stays backed up. */
  write(frame: ChatFrame): boolean | void;
}

/** A live stream. */
export interface ChatStream {
  /** Stop sending and release the seat reference. Safe to call twice. */
  close(): void;
}

/** One player in one room. Cheap, idempotent to create; every method re-checks the player's state. */
export interface ChatSession {
  readonly name: string;
  /** Start a stream: the `hello` frame is written before this returns, then lines as they come. */
  open(sink: ChatSink): ChatStream;
  /** Check a line with the kit and, if it passes, deliver it to the room. Never throws. */
  send(input: { text: string }): SendResult;
  /** Mute or unmute a player, named by one of their lines or by the token from `muted`. `false`: nothing to do. */
  mute(input: MuteTarget & { on: boolean }): boolean;
  /** Report a line. The reporter is this session; the person is the line's author. Never rejects for a kit refusal. */
  report(input: { lineId: string; reason?: string; note?: string }): Promise<ReportOutcome>;
}

export interface RoomBroadcasterOptions {
  /** History kept per room for late joiners. `lines` 1 to 100 (default 50); `maxAgeMs` 1 000 to `EVIDENCE_MAX_AGE_MS` (default `EVIDENCE_MAX_AGE_MS`). */
  history?: { lines?: number; maxAgeMs?: number };
  /** Most players seated at once in one room. Default 500. A join over it is refused. */
  maxMembers?: number;
  /** Most open streams for one player in one room (tabs). Default 3. */
  maxStreamsPerMember?: number;
  /** Most open streams in the process. Default 5000. */
  maxStreams?: number;
  /** A comment line is written to every stream this often, so a proxy does not drop an idle one. Default 20 000. */
  heartbeatMs?: number;
  /** How long a seat with no stream and no request is kept before it is released. Default 120 000. */
  seatGraceMs?: number;
  /** A stream whose sink has refused this many writes in a row is closed (the client reconnects). Default 64. */
  maxBacklog?: number;
  /** Keys the seat ids. Default: random per broadcaster. Seat ids never leave the server. */
  seatSalt?: string;
  /** Check each member name with `cw.names.check`; a refused or empty name becomes `Player N`. Default true. */
  nameCheck?: boolean;
  /** Epoch-ms clock. Default `Date.now`. */
  now?: () => number;
  /** Runs `fn` once after `ms` and returns its cancel. Default: `setTimeout` (unref'd where the runtime has it). For tests. */
  schedule?: (fn: () => void, ms: number) => () => void;
  /** Where failures are logged (event and error class only). Default `console.warn`. */
  logger?: Logger;
}

export interface RoomBroadcaster {
  /**
   * A session for this player in this room, seating them if needed. `{ refused }` when the door is shut to them (a ban: `reason`
   * `banned`), the room is full or the process is at its stream limit (`full`), or `who` has neither an account nor a client key
   * (`unauthorized`; an address alone is never a chat identity). The routes turn `unauthorized` into 401 and `full` into 429; they are not
   * kit refusal reasons a line can get. Synchronous; never throws.
   */
  session(roomId: string, who: RawWho, member: ChatMember): ChatSession | { refused: WireRefusal };
  /**
   * Tell the open chat boxes of this person that a notice is waiting (and refresh their restriction). Call it from `platform.notify`.
   * Takes the subject id the kit gives that hook; nothing about it is sent.
   */
  noticePending(subject: SubjectId): void;
  /** End every stream in the room (`bye`, `room_closed`), drop its history, and `cw.rooms.close(roomId)`. */
  closeRoom(roomId: string): void;
  /** End every stream (`bye`, `shutdown`), stop the timers. The broadcaster is unusable afterwards. */
  close(): void;
  /** Counts for a health probe. */
  stats(): { rooms: number; members: number; streams: number };
}

/** `cw` is the kit; it must have a `rooms`, `chat`, `mutes`, `reports`, `doors` and `names` (the facade). */
export function createRoomBroadcaster(cw: Chatwarden, options?: RoomBroadcasterOptions): RoomBroadcaster;
```

Every option is validated when the broadcaster is built (`RangeError`, never echoing a value), like `playerRoutes`.

### 6.3 The routes (`@chatwarden/http/chat`)

```ts
export interface ChatRoutesOptions {
  /** Who is calling. Exactly the `identify` of `playerRoutes`: the same function can be passed to both. A caller with neither `accountId` nor `clientKey` is `401 unauthorized` (an address alone cannot chat). */
  identify: (req: KitRequest) => RawWho | Promise<RawWho>;
  /** May this player enter this room, and under what name? `null` is `403 forbidden`. Required: the kit does not guess who may be where. */
  join: (req: KitRequest, roomId: string, who: RawWho) => ChatMember | null | Promise<ChatMember | null>;
  /** Lines, mutes and reports per player. Default 30 per 10 000 ms. (The kit's chat rate, 3 per 5 s, still applies underneath.) */
  actionRateLimit?: NamesRateLimit;
  /** Stream opens per player. Default 10 per 60 000 ms. */
  openRateLimit?: NamesRateLimit;
  /**
   * When given, a request with an `Origin` header not in this list is `403 forbidden`. A request with no `Origin` is allowed. Default: not checked
   * (the JSON content type, below, already stops a cross-site form).
   */
  allowedOrigins?: readonly string[];
  /** Where failures are logged (event and error class only). Default `console.warn`. */
  logger?: Logger;
  /** Epoch-ms clock for the limits. Default `Date.now`. */
  now?: () => number;
}

export function chatRoutes(cw: Chatwarden, broadcaster: RoomBroadcaster, options: ChatRoutesOptions): RouteTable;
```

`NamesRateLimit` is the type `playerRoutes` already exports. The limiter class in `player.ts` moves to a shared, browser-safe
`limiter.ts` (it uses only a `Map`); the salted SHA-256 key it needs is replaced here by the broadcaster's seat key, which is already a
hash and carries no credential.

### 6.4 The HTTP routes

All paths are relative to the mount point (`/chat`). `:room` is a kit route param (1 to 64 of `A-Z a-z 0-9 _ -`). Every response carries
`cache-control: no-store`. Errors use the kit's shapes (`{ error, message }`).

| Route | Body | Answer | Errors |
| --- | --- | --- | --- |
| `GET /rooms/:room/stream` | none | `200`, `content-type: text/event-stream; charset=utf-8`, an open response of `ChatFrame`s | `401 unauthorized`, `403 forbidden`, `429 rate_limited` (with `retry-after`) |
| `POST /rooms/:room/lines` | `{ text: string }` | `200 SendResult` (a refusal is an answer, not an error) | `400 invalid_request`, `401`, `403`, `413 payload_too_large`, `429` |
| `POST /rooms/:room/mute` | `{ lineId: string, on: boolean }` or `{ ref: string, on: boolean }` | `200 { ok: boolean }` | `400`, `401`, `403`, `429` |
| `POST /rooms/:room/report` | `{ lineId: string, reason?: string, note?: string }` | `200 ReportOutcome` | `400`, `401`, `403`, `429` |

- **POST bodies must be `application/json`.** Any other content type is `400 invalid_request`. A cross-site HTML form can only send
  `application/x-www-form-urlencoded`, `multipart/form-data` or `text/plain`, so it cannot make a player speak. A cross-origin `fetch`
  with `application/json` needs a CORS preflight, which the kit never answers.
- A `banned` player: the stream answers `200` with one `bye` frame (`reason: 'banned'`, `until`) and ends; a POST answers
  `200 { ok: false, refused: { reason: 'banned', until, noticeId } }`.
- `retry-after` on a `429` is whole seconds, as on `/names/check`.
- No route returns a report id, a seat, a subject or a moderator field. `report` returns the count of reports left today and nothing else.

### 6.5 Streaming support in the adapter

`KitResponse` (`packages/http/src/types.ts`) gains one optional field, so a route handler can keep a response open:

```ts
export interface KitStream {
  /**
   * Called once, after the status and headers are sent. `write` appends text and returns `false` when the connection is backed up;
   * `end` finishes the response. Return a function the adapter calls when the client goes away or the response ends; it must stop
   * writing and release anything the stream holds.
   */
  start(sink: { write(chunk: string): boolean; end(): void }): () => void;
}
export interface KitResponse {
  status: number;
  headers?: Record<string, string>;
  body: unknown;
  /** When present, `body` is ignored and the response stays open until `start`'s sink ends it or the client leaves. */
  stream?: KitStream;
}
```

`toExpress` handles it: it sends the status and headers, adds `cache-control: no-store`, `x-accel-buffering: no` and
`content-type: text/event-stream; charset=utf-8` unless the route set them, calls `flushHeaders()`, disables the socket's Nagle delay,
calls `start`, and calls the returned cancel on `close`. The existing fields and the existing 500 path for a thrown handler are
unchanged. `createRouter` users who write another adapter (Fastify, a Worker) implement `stream` as they implement the rest of
`KitResponse`; the contract is documented in `matchRoute`'s comment. A response with `stream` is still passed through `withErrors`
before it starts, so `401` and `403` are ordinary responses.

## 7. Wire format

**Down.** `text/event-stream`. Each frame is one event: `event: <type>\ndata: <JSON>\n\n`, the JSON having no raw newline (JSON escapes
them). A heartbeat is a comment, `: ping\n\n`, every `heartbeatMs`. The first event is always `hello`. Example (one `snerp` reading, then a
line from `tarvo`):

```
event: hello
data: {"type":"hello","v":1,"epoch":"k7f2q9","room":"lobby","you":{"name":"snerp"},"maxLength":200,"summary":"Trash talk is part of the game. Harassment, threats and hate are not.","restriction":null,"lines":[{"id":"41","at":1800000001000,"name":"tarvo","text":"anyone for a round?"}],"muted":[]}

: ping

event: line
data: {"type":"line","line":{"id":"42","at":1800000009000,"name":"tarvo","text":"gg"}}
```

**Up.** JSON bodies on the POST routes (section 6.4). The answer to `lines` is the author's, direct:

```
POST /chat/rooms/lobby/lines   {"text":"hello"}
200 {"ok":true,"line":{"id":"43","at":1800000012000,"name":"snerp","text":"hello","mine":true}}

POST /chat/rooms/lobby/lines   {"text":"<a synthetic blocked term>"}
200 {"ok":false,"refused":{"reason":"blocked","rule":1}}

POST /chat/rooms/lobby/lines   {"text":"hello again"}   (restricted by a moderator)
200 {"ok":false,"refused":{"reason":"restricted","until":1800003600000,"byModerator":true,"rule":4,"noticeId":"n_9c1"}}
```

**Rules of the format.**
- A delivered line reaches the author twice (the answer to the POST, and `line` on every open stream of that player, including the
  one in the same tab). The client merges by `id`, so it is shown once.
- A line is delivered to a stream only when `cw.chat.visibleTo(room, viewerSeat, authorSeat)` is true at that moment.
- Unknown frame types and unknown fields are ignored by the client (a newer server stays readable). `v` changes only when a reader would
  misread a frame.
- Text on the wire is always the delivered text (starred if the profile stars), never the typed text. The author's input is cleared on
  `ok: true` and kept on a refusal, so a refused line never needs to come back from the server.
- `maxLength` for a frame field is enforced by the client reader: a name over 64 characters or a text over 1 000 is cut, a frame over
  64 KiB is dropped. (The server never sends them; this is a belt for a custom transport.)

## 8. What a line goes through

### 8.1 The path

```
POST /rooms/:room/lines { text }
  1. content type is application/json; body is an object with a string `text`        -> 400
  2. identify(req) has an account or client key                                       -> 401
  3. action rate limit (per player)                                                   -> 429
  4. join(req, room, who) returns a member                                            -> 403
  5. session(room, who, member): door check (`cw.doors.check('join', who)`), seat      -> { refused: banned | full }
  6. cw.chat.accept(room, seat, text)                                                  -> refused | delivered
  7. delivered: ring.append, then for every open stream of the room: visibleTo? write `line`
  8. answer the author
```

Steps 6 and 7 are the whole moderation story: the broadcaster has no filter, no rate limit for lines and no second opinion of its own.
Steps 3 and 4 are HTTP-level guards that make the request cheap to refuse; the line-level limits (200 characters, 3 lines per 5 s, and
slow mode when it ships) are the kit's.

### 8.2 The outcomes, and what the author sees

| `cw.chat.accept` says | Wire (`refused.reason`) | Fields | The box shows (words, section 13.4) |
| --- | --- | --- | --- |
| `empty` | `empty` | none | nothing (the client does not send blank lines; if one arrives it is silent) |
| `length` | `length` | none | "That message is too long. The limit is 200 characters." (the limit from `hello.maxLength`) |
| `rate` | `rate` | none | "You are sending messages too fast. Wait a moment." |
| `gate` | `gate` | none | "You cannot send messages here right now." |
| `blocked` | `blocked` | `rule` | "That message was not sent. It breaks a community rule." and "Community Rule 1." |
| `profanity` | `profanity` | none | "That message was not sent. Please leave out the swearing." (only under a profile that refuses swearing; the default stars it) |
| `restricted` | `restricted` | `until`, `byModerator`, `rule?`, `noticeId?` | The existing `RestrictedChatLine` replaces the input |
| the door (a ban) | `banned` | `until`, `noticeId?` | "You are banned, so you cannot join this chat." |
| `slow_mode`, `flood`, `duplicate` (when shipped) | the same | `retryAfterMs` | "Slow mode is on. You can send another message in 3 seconds." and Send waits that long |
| anything else | the string | whatever known fields it has | "That message was not sent." (and the wait, if `retryAfterMs`) |

The mapping copies `reason`, `until`, `byModerator`, `rule`, `noticeId` and `retryAfterMs` by name and nothing else. `retryAfterMs` is read
structurally and accepted only as a whole number from 1 to 3 600 000, so the code compiles and behaves the same against a core that has not
shipped pacing. A refused line is not in the ring, not in any frame, and not in a log.

What is not a refusal: a **mute** (section 3, ruling 5). A player a viewer has muted keeps speaking to everyone else and receives
`ok: true`; only the muter's streams skip the line. Nothing in any answer, frame or timing tells the muted player.

### 8.3 Behaviour with and without flood control

The design on slow mode, flood and duplicate lines (`docs/design/2026-11-12-flood-control-and-signals.md`) adds three reasons and a
`retryAfterMs` to the same result. Which lands first does not matter:

- **Flood control not shipped.** Core never returns those reasons. The broadcaster's mapping is by string, so there is nothing to
  compile against; the box's words for them exist and are unused. `rate` has no wait time, so the box shows its sentence and leaves
  Send enabled (a rate-refused line spends nothing, so pressing again costs the player nothing).
- **Flood control shipped first.** The broadcaster passes `retryAfterMs` through, the box holds Send until the time has passed and says how
  long, and the tests that drive real pacing through the real core (plan Task 11) run. No code in this feature changes.
- **This ships first.** Flood control needs nothing from it. Its design says the kit "has no chat box"; that sentence and its
  `RestrictedChatLine` `pace` prop remain true and unused here (the box says pacing in its own words, so it does not depend on
  `secondsLeft` or the `player.pace.*` keys). When both are in, a later cleanup can point the box at those keys; it is not needed.

## 9. History

- **What it is.** A ring per room inside the broadcaster: `{ id, at, seat, name, text }` for each delivered line, newest last. The seat
  stays on the server (it is how a line is resolved to an author for a mute or a report).
- **Bounds.** At most `history.lines` (default 50, at most the evidence buffer's 100) and never older than `history.maxAgeMs` (default
  `EVIDENCE_MAX_AGE_MS`, 15 minutes, and not above it). The age cap is the point: a line in the ring is a line the kit's evidence
  buffer still holds, so every line a player sees can be reported with full context. The ring is pruned on every write and every read,
  so a quiet room's ring still empties.
- **Per viewer.** On `open`, the snapshot is the ring minus every line whose author the viewer has muted (`cw.chat.visibleTo`), so a
  late joiner sees what an old joiner would have seen.
- **Late joiners and reconnects.** `hello.lines` is the snapshot. The client merges it by `id` into what it already has; a changed
  `epoch` replaces everything. There is no replay cursor.
- **Lifetime.** In memory in this process. Lost on restart (new epoch). Dropped by `closeRoom`. A room with no members and an empty ring
  is removed from the broadcaster's map.
- **No new table.** Chat text is not stored by the kit (the evidence buffer is memory too, and a report stores its own excerpt under the
  existing retention). If an adopter wants history that survives a restart, the answer is their own store behind a custom sink; the
  design does not need one (section 16).

## 10. Multi-process

Everything the chat path reads is already per process: the roster (`cw.rooms`), the evidence buffer, the `rate` limiter (and pacing,
when it ships). The ring follows the same rule. The supported arrangement in this release is the usual one for a websocket game:

**Route a room's connections, and its POSTs, to one process** (hash the room id, or use the platform's sticky routing; a single process
is the common case). Then history, mutes of the room's players, rate limits and reports behave exactly as on one process.

What a game that spreads one room over several processes needs, and why it is not shipped yet:

1. **A pub/sub hook.** A `RoomBus` the broadcaster publishes each delivered line to and subscribes to: `publish(room, line)` and
   `subscribe(handler) => unsubscribe`. Each process delivers remote lines to its own streams.
2. **Agreed ids.** Line ids and seat ids are per process. The bus would carry an origin and the ring would key lines by it; the seat
   salt (`seatSalt`) would be shared so a player has one seat id everywhere.
3. **Evidence.** A report needs the line in the evidence buffer of the process that files it. A line from another process is not in that
   buffer, so reports and mutes on remote lines need either evidence replication (core work) or routing the report to the origin.

Items 2 and 3 are why the hook is not shipped as a half-working option: it would display correctly and then fail on report. The
recommendation to adopters is the sticky room, documented in the README beside the pacing advice. Open question 4 asks whether to ship
the bus anyway.

A restart is a new `epoch`. The stream drops, the client reconnects with back-off, receives a fresh `hello`, and discards what it held.

## 11. Security

**Identity and access.**
- `identify` runs on every request, stream included; nothing is cached against a token. A caller with no account and no client key is
  `401`; an address alone is never a chat identity (the same rule as the player routes).
- `join` is required and decides both access and display name; there is no default, so a room id in a URL cannot create a room.
- The seat id is a salted hash of the identity (`makeHasher(salt)`, per broadcaster unless `seatSalt` is given). The same player in two
  tabs shares one seat, so one rate budget and one set of mutes. The raw credential is hashed at once and never stored or logged.
- The reporter's seat is the session's, from `identify`; a body field cannot name another. The reported player is the line's author
  from the ring, not a body field (so no one can file a report against an arbitrary seat), and a line the reporter cannot see
  (muted author) is `not_found`.

**What may leave the server.**
- Frames and answers hold only the fields in section 6.1. A test seeds distinctive values (client key, account id, IP, subject id,
  hash, seat id, moderator name) and scans every frame, answer, header and log line for them.
- `name` is the one player-visible string the game chose. It is a display name, not an identifier. A game whose `join` returns an account
  id as the name has leaked it itself; the README says so in one line. Names are checked with `cw.names.check` (a refused or blank name
  becomes `Player N`), trimmed, stripped of control characters and cut at 32.
- A refused line is never in the ring, a frame, an answer to anyone but its author (and there as a reason only), or a log. The kit's
  evidence buffer holds a blocked line for a report, as today; the broadcaster adds no second copy.

**Abuse limits.**
- The line limits are the kit's (200 characters, 3 per 5 s per seat, pacing when set).
- HTTP guards before the kit: `actionRateLimit` per player (default 30 per 10 s) over lines, mutes and reports together; `openRateLimit`
  (default 10 per minute); `maxStreamsPerMember` (3), `maxStreams` (5 000) and `maxMembers` per room (500), each a `429` with `retry-after`;
  the 64 KiB body cap. The limiter keys are the seat ids (already hashes); it holds at most 10 000 keys.
- Reports keep the kit's own limit (10 per reporter per 24 h) and refusals; the box shows them through `ReportDialog`.
- A slow or dead reader cannot hold memory: the heartbeat's write fails or returns `false`, and a stream backed up for `maxBacklog` writes
  is closed. The seat is released `seatGraceMs` after its last stream and last request.

**Cross-site and hostile input.**
- A POST must be `application/json` (section 6.4); `allowedOrigins` adds an `Origin` allow-list. The kit does no CORS, so a page on
  another origin cannot read the stream or send JSON with the player's cookies.
- The stream carries `cache-control: no-store`, `x-content-type-options: nosniff` and `x-accel-buffering: no`.
- The client renders names and text as React text nodes. There is no `dangerouslySetInnerHTML`, no link detection, no markdown, and the
  static scan that bans injected HTML in player-react covers the chat code too. A line of `<img src=x onerror=...>` is shown as that
  text.
- The client reader validates every frame (types, lengths, a closed set of frame types) and ignores what it does not understand.

**Operations.** Behind a reverse proxy, `identify` must read the real client IP from the proxy's header (the player routes' note applies
unchanged). Do not put `compression` middleware over `text/event-stream`. Idle timeouts at a proxy should exceed the 20 s heartbeat.

## 12. Privacy

- **Held, and for how long.** The ring holds delivered text, the display name, a time and a server-side seat for at most 15 minutes and 50
  lines per room, in memory, never written to the store. A restart or `closeRoom` clears it.
- **Not held by the broadcaster.** Refused text; credentials; IPs (the kit hashes the IP at seating, as it does for any seated player).
  Nothing is added to the store, so retention, purge and the privacy export (when it exists) are unchanged.
- **Logs.** Event names and error classes only (`chatwarden.chat_stream_failed`, ...), through `safeWarn`. Never a line, name, room id,
  seat or credential. Failures are throttled like the other hot-path logs.
- **Players see only their own state.** The restriction, the notices nudge, the muted list (their own mutes, by name and an opaque token)
  and their own refusals. They never see that they were muted, reported, or why a line of someone else's did not appear.
- **Names.** Visible to every player in the room, as in any chat. The game owns what a name is.
- **Minors and the strict profile.** Unchanged: the profile decides what `accept` allows; the box adds no path around it.

## 13. The box: UI, accessibility, theming, words, size

### 13.1 What the player sees

```
 ┌──────────────────────────────────────────────┐
 │ tarvo   anyone for a round?                  │
 │ tarvo   gg                               ⋯   │   ← options appear on hover, focus, and always (dimmed) on touch
 │ snerp   hello                                │   ← own lines: name in the accent colour
 │                                              │
 ├──────────────────────────────────────────────┤
 │ Say something                        [ Send ]│   ← one input, one button; ⋯ at the corner opens Chat options
 └──────────────────────────────────────────────┘
```

- **The list**: name and text on one line that wraps; consecutive lines by the same name show the name once. No avatars, bubbles, times
  or timestamps by default (the `at` field is on the `<time>` element's `datetime` and `title` for those who hover).
- **The input**: one-row text area that grows to four rows. Enter sends; Shift+Enter adds a line break; Enter is ignored while an IME
  composition is open. A character counter appears only in the last 20 characters. Send is disabled while a request is in flight, or
  while a wait from `retryAfterMs` runs.
- **A refusal** appears as one line under the input (`role="status"`), in red only for failure words, with the draft kept in the input.
  It clears on the next keystroke or after 8 seconds, except a wait (clears when the wait ends).
- **A restriction** replaces the input with `RestrictedChatLine` (its sentence, its referee card). When `until` passes, the input
  returns by itself. Banned or room closed: the box shows one sentence and no input.
- **Connection**: a quiet line "Connection lost. Trying again." appears only while reconnecting; nothing when open.
- **Report and mute**: the options control on another player's line opens a small inline row with **Report** and **Mute <name>**.
  Report opens the existing `ReportDialog` for that line (name and quoted text). Mute hides that player's lines and shows a one-line
  confirmation with **Undo** for 8 seconds.
- **Chat options** (the one door, a control at the box's corner): **Muted players** (each with Unmute), **Read the rules** (only when
  `onOpenRules` is given) and the profile's one-line standard. Nothing else is added in this release.

### 13.2 Accessibility

- The list is `role="log"` (implicitly `aria-live="polite"`, `aria-relevant="additions"`) with an accessible name (`title`), and is
  focusable (`tabIndex=0`) so keyboard users can scroll it.
- **The snapshot is not announced.** The log's live region is turned on after the first `hello` has rendered, so joining does not read 50
  lines aloud. Lines that arrive afterwards are announced. Own lines are announced too (it confirms the send); a hidden line is silent.
- Each line reads "name: text" (a visually hidden colon). Names and text are text nodes. The own name reads "You".
- Scrolling: pinned to the bottom while the reader is at the bottom (within 24 px); once scrolled up the view stays put and a
  "Jump to the latest message" button appears (a real button, in the tab order), so a keyboard or screen-reader user is never yanked.
- Keyboard: the whole box is operable without a mouse. Tab order is the log, each line's options control, the input, Send, Chat options.
  Escape closes an open options row or panel and returns focus to the control that opened it. The report dialog is the existing modal
  with its focus trap and focus return.
- Refusals, the connection line and the mute confirmation are `role="status"` regions that exist in the DOM before they have text, so
  they are announced (a region inserted with text is often missed).
- Targets are at least 2.25 rem tall; the focus ring is the stylesheet's existing accent ring; every colour pair meets 4.5:1 in both
  schemes (the neutral tokens already do); no information is colour alone (refusals have words).
- `prefers-reduced-motion`: the box has no animation to remove; scrolling to the bottom is instant.

### 13.3 Theming

`chat.css` follows the contract in `styles.css`: every rule under `.cw-player`, every colour, size and space a `--cw-*` custom property
with a private `--cwd-*` default, `light-dark()`, the game's own font. It adds three tokens: `--cw-chat-height` (the list's height,
default `20rem`; set `height` on the box's `className` to override), `--cw-chat-gap` (space between lines) and `--cw-chat-name-width`
(unused unless a game wants aligned names; default `auto`). Colour is used only where it means something: the accent for the player's own
name and the Send button, red for a failure line. The root is `Root` from `ui.tsx` (`cw-player`), so `theme` and `className` work as on
every other component, and a game can restyle the box from its own stylesheet.

It is lazy-friendly by construction: the box is one module graph behind `@chatwarden/player-react/chat`, with `sideEffects` declared for
`chat.css` only, so `import('@chatwarden/player-react/chat')` is one chunk, and nothing in it runs until `ChatBox` or `sseTransport` is
called. `@chatwarden/http/chat` is server code: nothing in it reaches a player's bundle.

## 14. Tests that pin it

Test-first and broad, targeted runs only, a fake clock and a fake scheduler throughout (`now`, `schedule`), the real core over the memory
store (as `packages/player-react/test/world.ts` does) and the real routes. Names are indicative; the plan gives each task its exact list.

**Wire (`packages/http/test/chat-wire.test.ts`, `packages/player-react/test/chat-wire.test.ts`)**
- The two copies of the wire types are assignable to each other in both directions (type-level `expectTypeOf`), and `CHAT_WIRE_VERSION` is equal.
- Encoding: every frame is one `event:` and one `data:` line and a blank line; a text of `\n`, `\r`, U+2028 and a 200-character line never splits an event.
- The reader (client): accepts every frame the server writes; ignores unknown types and fields; drops a malformed frame, a frame over 64 KiB, a name over 64 and a text over 1 000 characters (cut, not dropped, for name and text); never throws for any JSON value, `__proto__` keys, arrays, `null`.
- The SSE parser: events split across chunks at every byte boundary; comments ignored; CRLF; a final event with no blank line is not emitted.

**Broadcaster (`chat-broadcaster.test.ts`, `chat-history.test.ts`, `chat-mutes.test.ts`, `chat-report.test.ts`, `chat-lifecycle.test.ts`)**
- Delivery: a delivered line reaches every other open stream and the author's streams (with `mine`), in order; the author's answer carries the same `id`.
- Refusals, one per reason the core produces today (`length`, `rate`, `blocked`, `profanity` under a refusing profile, `restricted`, `gate` from a closing gate, `banned` at the door): the author's answer has exactly the allowed fields; no other stream, ring, log or later snapshot contains the text.
- Pacing refusals (`slow_mode`, `flood`, `duplicate`) with a scripted facade: `retryAfterMs` is copied when a whole number 1 to 3 600 000 and dropped otherwise (`0`, `-1`, `1.5`, a string, `Infinity`).
- Mutes: a muted author's lines skip only the muter's streams; the author's answer is unchanged; `hide` removes the author's earlier lines from the muter's open streams; a later snapshot omits them; unmute by `ref` works only for the muter; a `ref` from another room or player is a no-op; the author never receives any frame about the mute.
- History: at most `history.lines`; a line older than `maxAgeMs` is gone (also in a quiet room); `maxAgeMs` above `EVIDENCE_MAX_AGE_MS` or `lines` above 100 is a `RangeError`; per-viewer filtering; `closeRoom` empties it; a restart (new broadcaster) has a new `epoch`.

## 15. Risks

- **A second chat path in tiny-chat.** tiny-chat keeps its WebSocket protocol (its 1 900 lines of tests are the kit's integration proof
  for the hand-wired route) and gains the HTTP chat beside it. Two paths in one example is more to read. Mitigation: the README
  says which is which; the server file's header names both; the HTTP chat is the recommended starting point.
- **SSE through a proxy that buffers.** Some proxies buffer a response until it fills. Mitigation: `x-accel-buffering: no`, a heartbeat,
  the README's proxy notes, and a client that treats "no `hello` within 10 s" as a failed attempt and retries (it then shows the
  reconnecting line rather than a blank box).
- **`KitResponse.stream` is an addition to a shared type.** Every adapter author sees a new optional field. It changes nothing for a
  route that does not use it, and `toExpress` is the only adapter in the repo. The contract is documented where adapter authors read it.
- **Per-process state.** Stated in section 10. A game that scatters a room across processes gets lines that display and reports that
  fail. Mitigation: sticky routing advice in two READMEs and the options table; the bus is a follow-up with its prerequisites named.
- **The 15-minute history is the evidence window, not a product choice.** A game that wants an hour of history cannot have it without
  evidence for those lines. That is the right default (nothing is shown that cannot be reported) and a limit adopters will notice.
- **Display names.** The kit checks them only against the matcher. A `join` that returns a stored account id as the name leaks it. Mitigation: the
  README line, the `name` doc comment, and the check that refuses an empty or blocked name.
- **Bundle growth in a game.** The chat code is a separate subpath and chunk; a game that imports it eagerly pays about 4 to 5 KB gzipped. The
  size test pins the ceiling.
- **React 18.3.** The package supports 18.3 and 19. The chat code uses only `useId`, `useRef`, `useReducer`, `useEffect`, `useState`,
  `useCallback` and `useSyncExternalStore` (all in 18.3). The test suite runs on 19, as for the other components.
- **The site demo is a heavy adopter.** Its chat pane is bespoke (avatars, inline "Blocked" stamps, a scripted tour that points at an
  always-visible Report button). Swapping it is its own change with its own review (question 7).
- **A new route family expands the surface.** Four routes, all behind `identify` and `join`, rate limited, JSON only. The security tests
  are the contract.

## 16. Not in this release

- A pub/sub hook for several processes (section 10) and any shared state.
- Channels, whispers, teams, spectators, typing and presence, read markers, reactions, pins, quick chat, emoji, markdown, links and
  translation.
- Moderator removal of a line from the room, edit and delete by the author, and "hold for review" (the product scope lists them).
- A WebSocket transport in the box (a game wraps its own with `ChatTransport`) and a WebSocket server adapter in http.
- History that survives a restart, or any chat table in a store.
- Wrappers for Vue or Svelte (the `ChatTransport` and the pure reducer are the seam, as for the hub's headless controller).
- A virtualized list (200 lines is the cap; it renders plainly).
- Per-player chat settings (hide profanity for me, chat off, team only).
- A site copy change. The headline flips only after the release is on npm and has run (follow-up in `docs/plans/follow-ups.md`).
- The site demo adopting the box (question 7).

## 18. Open questions

Each has a recommendation; the controller rules.

1. **SSE or WebSocket as the default.** *Recommended: SSE down plus POST up* (section 5): no dependency, works through proxies, one auth
   story, and the volume does not need two-way framing. A WebSocket stays possible through `ChatTransport`.
2. **Where the broadcaster lives.** A new `@chatwarden/http/chat` subpath that is also exported from the root. *Recommended: yes,* mirroring
   `@chatwarden/http/admin`: browser-safe, so the site demo and tests run it in a page, and no change to core.
3. **`ChatBox` from a subpath, or the main entry.** *Recommended: subpath only* (`@chatwarden/player-react/chat`): the main entry keeps its
   10 KB budget and its export lock, and the box is one lazy chunk. Cost: adopters import from a second path.
4. **Ship the multi-process bus now.** *Recommended: no.* It would display and then fail to report (section 10, items 2 and 3). Ship the
   sticky-room advice and revisit when core can share evidence.
5. **Does history match the evidence window (15 minutes, 50 lines).** *Recommended: yes, as the ceiling,* configurable downward. A
   longer history shows lines that cannot be evidenced.
6. **Should the default `join` exist (any identified player, any room, `Player N`).** *Recommended: no, `join` stays required.* A room id
   in a URL must not create a room, and a name is the game's to give.
7. **When does the site demo adopt the box.** The owner wants the demo to use it. *Recommended: a separate PR right after the release
   branch is green,* not inside it: the demo has about 4 000 lines of tests, a scripted tour aimed at an always-visible Report
   button, and inline "Blocked" stamps that the box (by design) puts in a status line. The release does not wait for it; the headline
   copy flip waits for both.
8. **Does the box need an "actions always visible" mode** (for the demo's tour, or a game that wants Report on every line)? *Recommended:
   no.* It adds a prop and a visible control for everyone; the tour can target the options control. Revisit if an adopter asks.
9. **Show the profile's one-line standard above the list by default.** *Recommended: no, it lives in Chat options;* a game that wants it
   visible can render `cw.summary` itself from `GET /rules`. The clean core wins.
10. **Seat sharing across tabs.** One player in two tabs shares one seat (one rate budget, one set of mutes). *Recommended: yes.* The
    alternative (a seat per stream) doubles a player's budget by opening a tab, which defeats the rate limit.
